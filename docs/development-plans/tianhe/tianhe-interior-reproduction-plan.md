# 天和核心舱内部复现开发计划

## 目标

以公开资料和用户提供的“带大家参观中国空间站内部”视频为观察依据，直接完成天和核心舱一个可进入、可观察、可交互的真实感第一人称场景。第一阶段就要求真实的舱壁面板、扶手、设备柜、线缆、睡眠区、灯光和材质，不把灰盒作为交付目标，也不把未公开的工程细节伪装成官方结构。

## 当前实施状态（2026-10-19）

2026-10-21 视觉复核：以本地小红书视频的舱内帧为依据，重新调整了主通道的面板比例、顶棚抓手与灯带、服务接口和线缆、摄影设备层次、睡眠袋缝线及材质粗糙度。工作照明改为更均匀的白色漫射，避免局部灯具把面板照成纯白；第一视角出生点距舱底约 1.92 米，处于成年人视线高度。新增设备凸出部分同步扩大碰撞体，保留微重力移动。该模型仍是基于可见影像的近似复现，未公开的内部构造不按官方设计宣称。

首个天和核心舱真实感垂直切片已经接入网页，当前覆盖视频中可明确复核的主通道、设备带、大型摄影机、蓝色扶手/绑带、线缆、睡眠袋和端部圆形舱门。资产以单一 `public/models/tianhe-interior.glb` 发布，由 `tools/build_tianhe_interior.mjs` 生成；运行时不包含程序化备用舱或旧灰盒。

已完成 `Three.js + Rapier` 第一视角闭环：Pointer Lock 鼠标观察、键盘六向推进、滚转/回正、低阻尼微重力、速度上限、球形玩家刚体、固定 `60 Hz`、CCD、扶手球形关节抓握，以及照明、通信、就餐、睡眠、锻炼五类首批交互。问天和梦天没有接入占位舱内场景。

自动化物理验收直接调用与网页相同的 `TianhePhysics` 生产模块。六向增强推进后的边界坐标为：前后约 `±6.523 m`、左右约 `±1.363 m`、上下约 `±1.153 m`，均被实体碰撞体阻挡在合法舱内容积内；连续 `36,000` 个固定物理步的十分钟模拟没有出现越界。浏览器验收另行检查正式 GLB 加载、前进输入响应、HUD 状态、外部 UI 隐藏和控制台错误。

本次垂直切片仍受公开影像角度与清晰度限制，不宣称是官方 CAD 或完整工程级复刻。通信、就餐和锻炼已提供基于公开功能资料的简化交互，完整设备细节以及卫生、医监区域仍属于后续扩展范围，不能把未被影像或资料确认的结构补写成确定事实。

## 交付策略：真实场景垂直切片

第一阶段选择视频中最清晰、最容易复核的一段内部空间作为完整垂直切片：从圆形入口/节点方向进入，沿长向舱体看到连续白色面板、蓝色扶手和两侧设备带，最终抵达睡眠区。这个切片必须从一开始就包含真实感几何、材质、灯光、设备外形和第一人称交互；后续再沿同一坐标系扩展到就餐、通信、锻炼和医监区域。

垂直切片的完成标准是“拿视频截图对比时，画面构图、材质层次、设备密度和可移动方向都能对应”，而不是“先放几个方块验证流程”。任何临时占位几何只能存在于开发分支的短期调试中，不得作为阶段成果或最终展示。

脚本使用 Chrome 的视频解码器，按指定采样率将每一帧导出为 JPEG，并生成 `manifest.json`：

```powershell
node tools/extract-video-frames.cjs `
  references/source-material/tianhe/interior-video/xiaohongshu-tianhe-interior.mp4 `
  references/source-material/tianhe/interior-video/frames-30fps `
```

调研阶段可以先用 `2` 或 `5` fps 快速浏览；需要逐帧对照时使用 `30` fps。导出的帧属于本地参考资料，目录被 `.gitignore` 忽略，不应直接提交到 GitHub。

## 已确认的公开功能分区

中国载人航天工程网公开资料将天和核心舱密封舱内划分为六类区域：

1. 工作区：任务操作、通信和实验支持；
2. 睡眠区：独立睡眠环境和个人收纳；
3. 卫生区：卫生设施与隐私隔断；
4. 就餐区：微波炉、冰箱、饮水机、折叠桌等；
5. 医监医保区：健康监测和医疗保障设备；
6. 锻炼区：太空跑台、太空自行车、抗阻拉力器。

公开资料还提到情景照明可由手机 App 控制，具备航天员之间及天地之间的语音/视频通信能力，并支持电子邮件通信。上述内容可以作为第一批面板交互的事实依据；面板的具体品牌、按钮布局和线缆走向，若视频或公开图像无法确认，只做低细节游戏化近似。

## 视角与空间表现

### 摄像机

- 默认第一人称，眼高不固定，采用“漂浮在舱体中心线附近”的相机；
- 允许 6DoF 观察：前后、左右、上下平移以及俯仰/偏航/滚转；
- 进入舱段后保留轻微相机漂移和惯性，避免像地面 FPS 一样有固定脚底；
- 通过可见扶手、舱门圆环和设备边缘建立方向感。

### 桌面端输入约定

| 输入 | 行为 | 设计约束 |
|---|---|---|
| 单击画面 | 锁定鼠标并进入第一视角 | 使用 Pointer Lock；`Esc` 释放鼠标 |
| 鼠标水平/垂直移动 | 偏航/俯仰 | 不改变玩家位置，不加入地面 FPS 的走路晃动 |
| `W` / `↑`、`S` / `↓` | 沿当前镜头方向前推/后推 | 施加加速度，不直接改相机坐标 |
| `A` / `←`、`D` / `→` | 沿当前镜头右轴左移/右移 | 允许与前后、升降同时输入 |
| `Space`、`Ctrl` | 沿当前镜头上轴上移/下移 | 不使用世界固定的“地面上下” |
| `Z`、`C` | 左滚转/右滚转 | 低角速度，松键后平滑停止 |
| `Shift` | 短时增强推进 | 仍受舱内安全速度上限和连续碰撞检测约束 |
| `F` | 抓住/松开视线中心附近扶手 | 抓握期间以扶手为约束点，不瞬移玩家 |
| `R` | 逐步回正视角 | 只消除滚转，不改变位置或绕过碰撞 |

键位只描述桌面端首期方案。交互面板使用视线中心准星加 `E` 确认，避免 Pointer Lock 状态下还要求用户移动系统光标。

### 微重力交互

- 默认没有重力加速度，松手后保持速度并逐渐阻尼；
- 抓住扶手后沿舱体轴线移动，释放时保留一小段惯性；
- 推离墙面/设备可产生可控反作用速度；
- 重要交互物体使用吸附/软约束，防止用户把关键面板推离场景；
- 设置“演示模式”：自动沿预设路径漂浮，便于第一次体验和视频录制。

微重力移动必须由加速度、速度、阻尼和接触响应共同产生，不能每帧按键后直接给相机坐标加固定距离。首轮手感参数以真实比例场景为基准调校：普通推进加速度约 `0.8-1.2 m/s²`，安全巡航速度约 `1.2 m/s`，增强推进上限约 `2.0 m/s`，线性阻尼保持较低；最终数值以不晕动、可在狭窄设备间停住和不发生碰撞穿透为准。

不加入上下起伏、脚步声、自动落地或固定眼高。墙面接触采用低反弹和适度摩擦，让玩家可以轻触停靠，也能沿舱壁缓慢滑动；猛烈撞击只衰减法向速度，不产生夸张弹跳。

## 防穿模与物理实现计划

### 技术选择

- 使用 `@dimforge/rapier3d-compat` 作为舱内刚体、碰撞查询和连续碰撞检测引擎，不自行编写简化碰撞物理；
- Three.js 只负责渲染，Rapier 负责玩家位姿、速度和接触；相机挂在玩家物理体上，任何移动都先通过物理世界求解；
- 使用固定 `60 Hz` 物理步长和时间累积器，渲染帧率变化不能改变推进速度或碰撞结果；
- 玩家使用半径约 `0.30 m` 的球形安全碰撞体并开启 CCD。球体在任意偏航、俯仰和滚转角下占用空间一致，适合首版无可见身体的 6DoF 第一视角；半径必须在入口、睡眠区和最狭窄通道实测后锁定，不能只用一个无体积的相机点；
- 镜头近裁剪面控制在约 `0.03-0.05 m`，相机与碰撞体外缘保留头部安全距离，避免物理体没穿墙但画面先切进面板。

### Blender 碰撞资产

正式舱内 GLB 同时导出可见模型和专用碰撞集合，但两者职责分离：

| 集合/节点 | 内容 | 要求 |
|---|---|---|
| `VIS_Tianhe_Interior` | 舱壁、面板、设备、扶手和软质物体的高保真可见网格 | 不直接作为全量物理碰撞体 |
| `COL_Tianhe_Hull` | 封闭的舱壁内表面、端壁、舱门和通道边界 | 必须水密、法线一致，没有能让玩家漏到外部的裂缝 |
| `COL_Tianhe_Equipment` | 会阻挡身体的设备柜、桌板、摄影设备和大型突出物 | 采用简化凸包或基础碰撞体，轮廓必须覆盖可见实体 |
| `COL_Tianhe_Handrail` | 可碰撞、可抓握的扶手与环形结构 | 碰撞体与交互锚点共用同一局部坐标系 |
| `SPAWN_Tianhe_Entry` | 第一视角出生位姿 | 周围必须有完整安全间隙，不能与碰撞体相交 |
| `PORTAL_Tianhe_*` | 已完成的舱门连接面 | 只在连接场景真实存在时开放；尚未制作的出口必须有可见舱门和实体碰撞封闭 |

碰撞壳必须跟随真实模型同步修改。同一次 Blender 迭代中，只要舱壁、设备或门洞改变，就必须更新对应 `COL_*`，不能保留旧碰撞网格，也不能用不可见大盒子掩盖不匹配的几何。

### 玩家移动求解

1. 读取键盘状态，将输入合成为相机局部坐标中的三维推进方向；
2. 对角输入归一化，向玩家刚体施加推进力或目标加速度；
3. 物理引擎按固定步长积分速度，通过 CCD 求出本帧最早碰撞时间；
4. 接触舱壁或设备时由 Rapier 接触求解器消除向内速度并保留合理的切向滑动，控制器不重复编写一套碰撞响应；
5. Rapier 求解后的刚体位姿作为唯一相机位置来源，渲染层不得再次修改相机位置；
6. 鼠标只更新观察四元数，`Z/C` 更新滚转；球形物理体不跟随观察旋转，避免转头本身改变占用空间或把玩家推出舱外；
7. 抓握扶手时建立物理约束或锚点约束，松开后从约束状态连续继承线速度，不进行位置跳变。

不得把“越界后传送回出生点”“每帧把坐标夹在包围盒内”或“检测到墙后把相机硬拉回去”作为防穿模方案。这些做法会掩盖碰撞壳裂缝和高速隧穿。开发期越界检测只用于中止测试并报告发生位置、速度和碰撞体名称，修复必须落在碰撞资产或物理解算上。

### 防穿模专项测试

- 出生测试：玩家生成后与任何碰撞体都没有重叠，并能看到入口的正确朝向；
- 六向测试：在舱内每个主区域分别持续按住前、后、左、右、上、下，不能离开封闭空间；
- 高速测试：增强推进状态下正撞舱壁、斜撞墙角、掠过设备边缘，CCD 不得漏碰；
- 门缝测试：逐一检查圆形舱门、面板接缝、设备柜背面和舱体端盖，不得存在可钻出的缝隙；
- 旋转测试：贴近墙面完成 `360°` 偏航、俯仰和滚转，镜头不能切入墙后或被旋转推出舱外；
- 帧率测试：在 `30/60/120 fps` 渲染条件下重复同一输入录制，最终位置和碰撞结果保持在可接受误差内；
- 长时测试：连续自由移动至少 `10` 分钟，场景外停留帧数必须为 `0`；
- 自动化测试：沿入口、设备带、睡眠区设置若干封闭体积断言，每次构建验证玩家中心始终位于合法舱内容积中；失败时输出坐标、速度和最近碰撞体，不自动恢复。

## 实施阶段

### P0：真实模型与碰撞基线（已完成首个垂直切片）

- 完成入口、主通道、连续设备带和睡眠区的真实比例可见模型；
- 在同一 Blender 文件中制作 `COL_Tianhe_Hull`、主要设备碰撞体、扶手碰撞体和出生点；
- 检查碰撞壳水密性、法线、门洞连接关系和单位比例；
- 导出单一最新 GLB，删除被替代的舱内模型和碰撞资产。

完成条件：可见模型已经达到本计划的真实感垂直切片要求，碰撞壳能独立显示审查，并且所有未完成出口均被实体舱门封闭。

### P1：封闭物理世界（已完成）

- 接入 Rapier 固定步长、静态舱体碰撞、球形玩家刚体和 CCD；
- 从 `COL_*` 节点建立静态三角网格、凸包和基础碰撞体，不从高面数可见模型自动猜测碰撞；
- 验证出生点安全间隙、所有未完成舱门的封闭状态，以及入口到睡眠区的连续合法空间；
- 建立仅供开发使用的碰撞调试视图，逐项对齐可见表面与碰撞边界。

完成条件：即使直接给玩家物理体施加六个方向的测试速度，也无法离开舱内合法空间，且不会卡入设备。

### P2：第一视角与鼠标观察（已完成）

- 接入 Pointer Lock、鼠标偏航/俯仰、`Z/C` 滚转和 `R` 渐进回正；
- 建立外部总览到天和舱内的明确场景状态切换，舱内不再启用 OrbitControls；
- 相机只跟随玩家物理体，不保存第二套可独立移动的位置状态；
- 增加准星、鼠标锁定状态和 `Esc` 退出行为。

完成条件：不按移动键时鼠标只能转动视角；视角在任意滚转角下保持连续，没有欧拉角翻转或突然回正。

### P3：微重力推进与碰撞闭环（已完成六向自动化验收）

- 实现前后、左右、上下六向推进和组合输入；
- 实现低阻尼惯性、速度上限、轻触停靠与增强推进；
- 用真实舱体尺度调节加速度、停止距离和镜头旋转灵敏度；
- 不添加地面行走、跳跃、重力或脚步晃动代码。
- 对舱门、墙角、面板缝、突出设备和高速斜撞进行专项修复；
- 将所有碰撞问题修正在当前模型和当前控制器中，不添加越界传送回退路径。

完成条件：玩家可从入口平稳漂移到睡眠区并沿原路线返回；全部防穿模专项测试通过，连续测试中没有任何一帧处于舱外或可见网格内部。P0-P2 的中间实现不得作为可试玩版本合入，首次合入必须同时达到本阶段条件。

### P4：扶手与物理反馈（抓握已完成，声音反馈待后续）

- 为视频中可确认的蓝色扶手和环形结构设置抓握锚点；
- 实现抓握、绕锚点调整身体方向、推离和释放后的速度继承；
- 添加轻微接触音、推进反馈和碰撞强度反馈，不使用夸张晃屏；
- 对容易晕动的用户提供降低惯性和禁用滚转的明确设置，这些是用户选项，不是隐藏回退逻辑。

完成条件：用户能只依靠扶手与推离动作穿过垂直切片，过程中不穿模、不瞬移、不会因抓握释放产生速度尖峰。

### P5：交互与最终验收（五类首批交互已完成，人工综合验收待完成）

- 在第一视角和 Pointer Lock 条件下接入视线准星、距离判定和 `E` 交互；
- 复核移动时所有面板、设备、线缆和扶手的近距离细节；
- 完成键盘操作、碰撞边界、微重力手感、晕动控制和性能验收；
- 桌面端稳定后再单独规划触屏和手柄映射，不让多输入端同时拖慢首个真实场景交付。

完成条件：新用户无需开发者协助即可从入口漂移到睡眠区、操作至少一个真实依据面板并返回，全流程没有穿模、卡死或控制权丢失。

## 建模拆分

1. `H0 真实舱体`：节点舱、大小柱段、后端通道、资源舱及连接门，按视频视角建立可进入的内部空间；
2. `H1 真实内装`：白色/浅灰面板、圆角过渡、接缝、检修盖、地板/顶板设备带、舱门和隔断；
3. `H2 真实设备`：照明、通信终端、折叠桌、收纳柜、摄影机、睡袋、锻炼设备和医监设备；
4. `H3 碰撞资产`：水密舱壳、设备凸包、扶手碰撞体、出生点和已确认连接口，与可见模型在同一坐标系维护；
5. `H4 可交互实体`：真实几何上的面板热点、状态卡、按钮反馈、灯光状态、门/桌/隔断动画；
6. `H5 真实感氛围`：微弱漂浮尘埃、设备风扇声、提示音、低频结构震动、舱内灯光和地球反照光。
